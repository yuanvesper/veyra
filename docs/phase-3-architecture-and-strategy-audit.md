## 结论摘要

1. Veyra 当前的真实形态是：**一个单文件、只读、面向 Java/Minecraft 崩溃日志的证据约束整理器，外加一个提示词级 Skill（JSON → 分析 → 回复草稿）**。它不是创作平台，也不存在独立命名的 “Veyra Core” 模块。
2. 当前仓库中**没有任何创作侧代码**：不生成项目、不生成代码/贴图/模型/音频、不构建、不运行、不测试 Mod、不管理依赖、不做可视化、不分发。这些不是“实现得弱”，而是尚不存在。
3. 真正可复用的资产不是崩溃解析器本身，而是四条方法论：**Python 拥有证据与行号的所有权**、**机器可读契约 + 版本策略**、**确定性校验先于 AI 输出**、**以合成用例和 unittest 守住回归**。
4. 从“日志诊断”到“Mod 创作平台”是产品轴的切换，不是同一模块的下一步迭代。若直接把 `triage_agent.py` 扩成平台，会得到一个难以测试和解释的单体。
5. 商业化切入点（二游角色主题、动态桌面、互动 Companion、原创素材）与当前代码资产几乎不重叠；它的第一批工程投入应放在**创作侧的项目/素材契约与离线打包**，而不是继续加深崩溃日志解析。
6. 建议的下一个实际开发任务是 Phase 3.1：**Pack 契约 + 离线打包最小纵向切片（人工素材、零模型调用）**。它用最小成本验证“写文件、管项目、校验产物、导出可分享成果”这条当前完全缺失的链路，并为后续接入生成模型留出稳定接口。详见第 9 节。

### 1.2 运行时数据流

只有一条主链路，两种模式、两种输出格式：

```text
日志文件
  → read_log()                     读取/解码/缺失与空文件处理
  → extract_evidence()             Python 生成 E1…En、真实行号、截断标记、注入检测
  → extract_environment()          Python 确定性抽取环境与 Mod
  → 本地模式 build_local_output()  规则生成 8 字段
     或 API 模式 build_messages() → call_model()（OpenAI 兼容）
  → validate_output()              证据 ID、环境依据、确定性根因措辞、文本行号
  → Markdown: render_report() → 原子写入 report.md / -o
     或 JSON: build_report_contract() → serialize_contract() → stdout / 原子写入
```

关键事实：

- **两种模式共用同一份环境抽取结果**，模型自报环境只进入 `model_environment`，不覆盖 Python 事实 [代码]。
- **证据 ID 与行号始终由 Python 生成**，JSON 序列化只是逐字复制，不重新编号 [代码]。
- **JSON 模式 stdout 只输出 JSON**，进度与错误全部走 stderr [代码][测试]。
- **Skill 不执行 CLI、不读日志、不联网**，它只消费维护者提供的 JSON 与玩家 Issue 文本 [文档]。
- **校验器与 CLI 相互独立**：CLI 不调用 `validate_issue_json.py`；Skill 侧需要维护者自行运行或按 SKILL.md 规则人工核对 [代码]。
- **Markdown 与 JSON 来自同一个已校验分析对象**，但 JSON 是更完整的契约（含 `mods`、`conflicts`、`warnings`），Markdown 是面向人的渲染 [代码]。

### 1.3 单文件内部分层

`triage_agent.py` 虽为单文件，但内部职责可清楚分为 8 段：

| 区段 | 行范围 | 职责 |
| --- | --- | --- |
| 常量与契约字段 | 44–162 | `VERSION=1.2.0`、`SCHEMA_VERSION=1.0.0`、环境字段、截断阈值 |
| 数据类型 | 163–219 | `ToolInfo` / `SummaryData` / `ModEntry` / `EvidenceEntry` / `ReportContract` |
| 日志读取与证据 | 220–425 | `read_log`、`extract_evidence`、注入检测、截断、格式化 |
| 模型输入与调用 | 426–657 | `build_messages`、`call_model`（urllib，timeout 60，temperature 0.2） |
| 环境抽取 | 658–855 | 版本/加载器/OS 归一化、Mod 列表、冲突候选 |
| 本地规则分析 | 856–933 | `build_local_output` 生成 8 字段 |
| 校验 | 934–1082 | 字段、证据 ID、环境依据、根因措辞、文本行号 |
| 写入与契约 | 1083–1265 | 同文件拒绝、原子替换、JSON 契约构造与序列化 |
| 渲染与 CLI | 1266–1651 | Markdown 渲染、中文参数解析、`main()` 串联 |

这种单文件分层对当前规模是合理的：107 个测试、无第三方依赖、可单文件复制运行。但它也意味着**任何新能力都会被迫塞进同一个文件**，这是 Phase 3 必须处理的结构性约束。

### 1.4 依赖与部署形态

- 仅标准库：`argparse/json/os/re/sys/tempfile/urllib/error/request/datetime/pathlib/typing` [代码]。
- Python 3.10+；无构建步骤；无 `pyproject.toml` / `requirements.txt` [代码]。
- 运行形态是**一次性进程**：读入一份日志，产出一份报告/JSON，然后退出。没有常驻服务、没有任务队列、没有缓存、没有项目状态。
- 配置全部来自环境变量：`TRIAGE_LOCAL_MODE`、`TRIAGE_DESCRIPTION`、`LLM_API_KEY` / `DEEPSEEK_API_KEY`、`LLM_BASE_URL` / `DEEPSEEK_BASE_URL`、`LLM_MODEL` / `DEEPSEEK_MODEL` [代码]。
- Skill 是**文件包**，由外部运行时（如 DSH）加载；安装器把 `skills/mod-issue-triage/` 整树复制到目标目录并写 `.veyra-install.json` 标记 [代码]。

### 1.5 架构判定

1. **它是一个“证据约束的文本整理器”，不是诊断引擎。** 它不理解游戏、不运行游戏、不读代码、不改代码；它只把日志中已存在的异常块变成可引用的证据，再让规则或模型组织语言。
2. **可信度来自所有权设计，不来自模型能力。** 证据 ID、行号、环境事实、写入行为都由 Python 掌握；模型只负责归纳与措辞。这是 Veyra 目前唯一真正的技术护城河。
3. **“Veyra Core”目前是概念，不是代码。** 仓库里没有 core 包、没有领域模型层、没有 adapter 接口。若未来要复用，需要先抽取出稳定的契约与校验层，而不是先命名一个模块。
4. **当前架构无法承载“创作”。** 创作需要项目状态、素材、构建产物、运行反馈与多轮修改；当前架构没有任何写侧状态模型。

## 3. 与最终目标的差距

最终目标是“用自然语言完成 Mod 的创作、修改、构建、测试、优化与分享”。以此为标尺，逐项对比如下。

| 目标能力 | 当前状态 | 差距说明 |
| --- | --- | --- |
| 自然语言创意理解 | 部分实现（仅问题描述） | 现在只理解“玩家遇到了什么问题”，不理解“我想做一个什么角色/玩法/美术风格”；没有需求结构化、澄清循环、创意约束（角色一致性、风格、受众、平台） |
| 游戏知识与 Adapter | 未实现 | 环境抽取硬编码 Minecraft/NeoForge/Forge/Fabric/Quilt 标签；没有游戏知识库、官方 API 能力表、版本矩阵、授权策略表 |
| Mod 项目生成 | 未实现 | 没有项目脚手架、manifest、模板、目录约定、依赖声明生成 |
| 代码创作 | 未实现 | 没有代码生成、补丁生成、API 绑定、编译错误闭环 |
| 贴图/材质/模型/动画/音频创作 | 未实现 | 没有素材生成、格式转换、尺寸/命名/调色板校验、版权元数据 |
| 构建与运行 | 未实现 | 没有 `subprocess`、没有 Gradle/工具链管理、没有游戏启动、没有沙箱与超时 |
| 自动化测试 | 未实现（对 Mod 而言） | 现有 107 个测试只验证 Veyra 自身；没有“生成 Mod → 启动 → 断言无崩溃”的 harness |
| 诊断与修复 | 部分实现（只读崩溃诊断） | 能整理崩溃日志；不能诊断构建失败、不能定位代码、不能生成修复补丁、不能验证修复 |
| 版本与依赖管理 | 未实现 | 只从日志读取版本号；没有解析、锁定、升级、冲突求解 |
| 兼容性管理 | 未实现 | 只在 JSON 中并列冲突值；没有兼容矩阵、自动选版、回归验证 |
| 预览与可视化编辑 | 未实现 | 无 UI、无渲染、无画布、无实时预览 |
| 导出、分享、分发 | 未实现 | 无打包格式、无发布流程、无平台对接、无许可证/署名产物 |
| 多游戏支持 | 未实现 | README Roadmap 仅提及 Unity/Unreal/Godot；代码没有任何 adapter 抽象 |

### 结构性差距（比清单更重要）

1. **数据模型差距**：当前输入是“一段文本”，输出是“一份报告”；创作平台的核心对象是“项目 + 规格 + 素材 + 构建产物 + 运行记录 + 版本历史”。两者不是同一类数据。
2. **执行能力差距**：当前进程不执行任何外部程序、不写项目文件（只写报告）。创作平台必须能安全地运行构建工具、游戏进程与测试脚本，并处理失败、超时、脏环境。
3. **创作能力差距**：当前没有任何生成式产物（代码、图像、音频）的接入点、缓存、成本核算与质量校验。
4. **权限与合规差距**：当前只处理用户主动提供的日志；创作平台要处理游戏 IP、官方 API、素材授权、用户生成内容的合规边界。
5. **交互与分发差距**：当前是“命令行一次运行”；创作平台需要多轮对话、项目持久化、预览、导出、分享。
6. **成本与配额差距**：当前本地模式零成本；一旦接入图像/代码模型，必须有配额、缓存、失败重试与单位经济模型。

**判断**：这不是 Phase 2C，而是产品轴切换。正确的做法不是把现有 CLI 改造成平台，而是保留它作为“诊断模块”，另建创作侧的最小闭环（见第 4、9 节）。

## 4. 推荐目标架构

### 4.1 设计原则

1. **CLI 优先，UI 最后。** 先用命令行 + 文件契约验证闭环，再谈 Web/桌面端。
2. **确定性内核，AI 在外围。** 文件布局、契约校验、素材规格、构建命令、证据与行号由 Python 掌握；模型只做理解、生成候选与措辞。
3. **Adapter 隔离游戏差异。** 每个游戏一个 adapter，声明它能读什么、能生成什么、允许什么、如何构建与测试。
4. **项目即状态。** 不引入数据库/向量库；项目目录 + manifest + 运行记录就是状态。
5. **每个 AI 产物都必须可校验。** 代码要能编译，素材要符合尺寸/格式，回复只能引用既有证据。
6. **不为凑模块而拆模块。** 只有出现第二个真实消费者时才抽取公共层。

### 4.2 模块划分与边界

| 模块 | 职责 | 输入 → 输出 | 依赖 | 首期是否建立 |
| --- | --- | --- | --- | --- |
| CLI / Entry | 参数、模式选择、退出码、人类可读输出 | argv → 文件/JSON | Core | 是（现有） |
| Core | 契约定义、证据模型、校验器、原子 IO、运行日志、错误码 | 任意产物 → 校验结果 | 无 | 是（从现有代码抽取） |
| Game Adapter | 游戏事实抽取、能力声明、版本矩阵、授权策略、构建/测试命令 | 日志/项目 → 事实与能力 | Core | 是（先做 Minecraft/NeoForge 适配器，包装现有逻辑） |
| Project Manager | 项目 manifest、规格（spec）、素材注册表、变更历史、导入/导出 | 用户意图 + 现有项目 → 项目状态 | Core | 是（Phase 3.1） |
| Creation Services | 代码生成、素材生成（贴图/图标/配色/文案）等可插拔后端 | spec + 参考素材 → 候选产物 | Project Manager、Core | 接口先定，实现后置 |
| Build & Test Engine | 沙箱内执行构建/测试命令、收集日志、判定成败 | 项目 → 构建产物 + 结果 | Adapter、Core | 后置（Phase B） |
| Diagnostic & Repair | 读取构建/运行日志，产出证据化诊断；修复建议默认不自动应用 | 日志 + 项目 → 诊断报告/补丁候选 | Core、Adapter | 现有 triage 迁入（Phase B） |
| Skill / Agent 层 | 对话式编排：收集意图、调用 CLI、解释结果、生成草稿 | 对话 → CLI 调用/文本 | CLI 契约 | 薄层，随 CLI 演进 |
| UI / Conversation | 可视化项目、预览、编辑、分享 | 项目状态 → 交互 | 全部 | 后置（Phase C） |
| Distribution | 打包、署名、许可证、发布渠道 | 项目产物 → 可分发包 | Project Manager、Core | 后置（Phase C） |

明确不单独建立的模块：

- **Context / Memory 服务**：早期用项目目录内的 `spec.json`、`decisions.md`、`runs/` 即可；没有跨项目长期记忆的真实需求前，不引入向量库或记忆服务。
- **多 Agent 编排器**：当前任务可由单进程 + 少量工具完成；多 Agent 只会增加不可解释性与成本。
- **账号/计费/市场**：在单机闭环跑通、有付费验证之前不建。

### 4.3 依赖关系

```text
CLI / Skill
   │
   ├── Core（契约·校验·IO·日志）
   │      │
   │      ├── Project Manager ── Creation Services（代码/素材后端）
   │      │        │
   │      │        └── Build & Test Engine ── Game Adapter
   │      │                                   │
   │      └── Diagnostic & Repair ─────────────┘
   │
   └──（后置）UI / Distribution
```

关键边界：

- **Adapter 只提供事实与命令，不直接写用户文件**；写入统一经过 Project Manager/Core。
- **Creation Services 不能绕过校验器**：代码候选必须编译，素材候选必须通过格式/尺寸/命名校验。
- **Build & Test 必须在沙箱与超时下运行**，输出结构化结果，而不是把原始日志直接丢给模型。
- **Diagnostic 默认只读**；任何自动修复必须经过“生成补丁 → 校验 → 用户确认”的闸门。
- **Skill 只能引用 CLI 产物中的证据 ID**，不得重新解析日志或创造行号。

### 4.4 与当前实现的衔接

- 现有 `triage_agent.py` 不拆毁，先作为 **Diagnostic 模块的 CLI 实现**保留。
- 从其中抽取 **Core** 的三样东西：契约序列化、证据模型、原子写与同文件保护。抽取时机是“第二个消费者出现时”，避免为抽象而抽象。
- 新增创作侧入口时，**不要**把项目/素材逻辑塞回 `triage_agent.py`；应新建独立 CLI 与包，复用 Core。

## 5. 现有资产保留与复用方案

### 5.1 Crash Triage 的定位

**结论：保留为独立能力，不并入创作主流程，也不重写。**

- 它解决的是“玩家提交日志后，维护者如何快速理解并回复”，这是真实且独立的需求，不应为了平台叙事而稀释。
- 它应成为未来 **Diagnostic & Repair 模块的第一个 adapter/实现**：输入是日志，输出是证据化诊断；未来构建失败诊断可以复用同一套“证据 ID + 行号 + 校验”的结构。
- 迁入方式：**包装，不迁移**。保留现有 CLI 与测试；新增 `diagnose` 子命令或独立入口调用它；不要在 Phase B 之前重写解析器。

### 5.2 复用清单

| 资产 | 复用方式 | 注意事项 |
| --- | --- | --- |
| 证据 ID / 行号所有权 | 作为所有诊断类产物的强制结构：`id/type/start_line/end_line/content/truncated` | 新模块不得自行编号或改写原文 |
| JSON 契约 + 版本策略 | 分析契约继续 1.x；创作侧另立 `pack` 契约（0.x），两者独立版本 | 不要把一个契约膨胀成万能对象 |
| 校验器模式 | 每个产物一个确定性校验器；退出码统一 0/2/1 | 校验器必须与 schema 同步，测试比较字段 |
| 原子写 / 同文件拒绝 | 打包、导出、项目写入全部复用 | 导出还要拒绝覆盖已有包（除非显式 `--force`） |
| 107 个测试 | 作为回归基线；任何抽取都必须保持全绿 | 抽取 Core 时先加契约测试，再移动代码 |
| Skill 提示词结构 | 新的“创作 Skill”复用“前置校验 → 分阶段 → 自检 → 边界”结构 | 创作 Skill 不得声称已构建/已测试，除非有运行记录 |
| Eval 用例格式 | 创作侧建立“输入 spec → 期望产物特征 → 禁止项”的用例 | 质量评估仍需人工或独立评审 |
| CI workflow | 扩为矩阵：Ubuntu + Windows；新增 pack 测试与安装器行为测试 | 不在 CI 里调用真实生成模型 |
| 安装器 | 继续服务 Skill 分发；未来可用于模板/示例包安装 | 安装器无单测，属于已知薄弱点 |

### 5.3 抽取节奏

采用“**先复制、后抽取**”：

1. Phase 3.1 新建 pack CLI 时，先写最小原子写与校验（允许少量重复），保证独立可测。
2. 当 triage 与 pack 都需要同一能力（如原子写、schema 校验、运行日志）时，再抽到 `veyra_core/`。
3. 抽取前先补契约测试；抽取后跑全量 107 + 新增测试。
4. 绝不在没有第二个消费者时预先设计插件系统、注册表或抽象基类。

## 6. 二游商业化策略

> 本节是产品假设与策略建议，不是已验证的市场结论。文中不引用任何未经核实的市场规模、收入或用户数据。

### 6.1 为什么从二游切入

- 二游玩家对角色有强情感连接，角色主题内容（壁纸、头像、桌面、互动小物件）天然具备**可分享、可展示、可二次传播**的属性。
- 这些产物可以完全在游戏客户端之外生成与使用，**不依赖游戏内 Mod 接口**，因此是当前唯一能合法、快速交付的创作形态。
- 它能以低成本验证三件事：用户是否愿意为“角色一致性 + 多产物成套”付费；生成质量是否达到可分享标准；创作侧的项目/导出链路是否成立。

### 6.2 合法边界（最高优先级）

- 只做**粉丝创作/同人周边**范围内的产物；逐游戏建立“官方同人政策/授权范围”清单，未确认的游戏不做。
- **不提取、不重打包游戏内素材**（模型、贴图、音频、UI）；参考图由用户提供或使用授权素材。
- **不向在线游戏客户端注入**、不做绕过检测的 Mod、不提供账号/进度修改。
- 游戏内 Mod 能力必须**逐游戏、按官方接口/授权**开放；未获授权的游戏明确标注“暂不支持游戏内 Mod”。
- 产物带 AI 生成披露、署名与使用范围说明；建立投诉/下架流程。
- 商业上避免把“二游角色周边”包装成“官方联动/官方授权”。

### 6.3 首批用户与首个产品

**首批用户**（按获取难度排序）：

1. 二游角色的二创画师/壁纸作者/头像店主——已有分享习惯，痛点是把一个角色做成一套风格统一的产物；
2. 主播/公会/应援团——需要成套视觉物料，迭代频繁；
3. 想给角色做“桌面伴侣/互动小物件”的普通玩家——零代码，但需要成品；
4. 小型 Mod 团队——未来向真 Mod 转化的桥梁。

**首个产品：Character Kit（角色主题包）**

输入：角色 + 风格/场景/用途（桌面、头像、应援、短视频封面）+ 参考图（可选）+ 授权声明。

输出（一个可分享的包）：

- 壁纸组（多分辨率/多构图）；
- 头像/表情/贴纸组；
- 配色板与字体建议；
- 短视频封面/应援图；
- 一段可直接发布的作品说明与署名；
- `manifest`（角色、风格、素材清单、许可证、AI 披露）。

关键不是“生成很多图”，而是**同一角色跨产物的身份一致性、成套规格正确、可迭代、可导出**。

### 6.4 付费结构（假设）

| 层级 | 内容 | 目的 |
| --- | --- | --- |
| 免费 | 单张低分辨率试作、崩溃日志诊断、模板浏览 | 获客与信任 |
| 按包/按次 | Character Kit 单包、加急、高清/多尺寸导出 | 验证付费意愿与单位成本 |
| 订阅 | 每月 N 包、角色一致性记忆、批量导出、商用许可 | 提高复购与留存 |
| 商用授权 | 主播/社团/店铺商用、去水印、扩大使用范围 | 提高客单价 |
| 创作者市场 | 模板/风格包/预设的分发与分成 | 后期生态，不在首期 |

价格必须由“单包模型成本 + 人工审核/客服 + 退款率”倒推；在拿到真实成本前，不做收入预测。

### 6.5 与“普通 AI 图片生成器”的差异

必须建立至少四项壁垒，否则会被通用生图工具替代：

1. **角色一致性**：跨 10+ 产物的脸型、配色、服饰、气质稳定；有参考图锁定与人工可调的种子/描述。
2. **成套规格**：不同平台的尺寸、安全区、格式、命名、透明通道一次到位，而不是让用户自己裁。
3. **项目与迭代**：包是可再次打开、修改、追加产物的项目，不是一次性聊天记录。
4. **授权与署名**：每个产物带来源、许可证、AI 披露，可安全分享/商用。
5. **通往真 Mod 的路径**：当用户想“让角色进入游戏”时，有明确的 adapter 与授权状态，而不是一句“暂不支持”。

### 6.6 从周边走向真 Mod

- 在 Character Kit 中埋入“想要游戏内版本？”的意图收集，形成 waitlist。
- 按游戏建立授权/技术可行性矩阵：官方 Mod 接口、沙箱限制、审核流程、可自动化构建程度。
- 第一个“真 Mod”目标应选择**授权明确且工具链可自动化**的游戏。以当前资产看，Minecraft Java / NeoForge 是唯一同时具备“现有解析器 + 可脚本化构建 + 开放生态”的候选；二游适配器在获得明确授权后再接。
- 真 Mod 的交付必须包含：可构建项目、依赖锁定、构建日志、运行/测试记录、证据化诊断；否则只是“代码片段生成器”。

### 6.7 验证计划（低成本、可证伪）

1. **5 个 concierge 包**：人工 + 模型混合制作，交给真实二创作者使用；观察是否发布、是否改稿、是否愿意付费。
2. **15–20 次访谈**：二创作者、主播、Mod 作者；重点问“最近一次为角色做一套物料花了多久/多少钱”。
3. **预售/定金**：在交付前测试付费意愿，而不是只问“会不会买”。
4. **一致性盲评**：同一角色 10 个产物，让 10 位目标用户判断“是否同一角色/是否愿意分享”。
5. **成本实测**：记录单包模型调用次数、token/图片成本、返工率。

建议跟踪指标：包完成率、首次分享率、7 日复购、付费转化、单包毛利、退款/投诉率、从周边到游戏内版本的意向转化。

### 6.8 不做什么

- 不做通用“提示词画廊”或纯图片生成器；
- 不做未授权游戏素材的提取/分发；
- 不做游戏内注入、破解、绕过检测；
- 不在没有授权的情况下宣称“支持某游戏 Mod”；
- 不用虚构的市场规模/收入数据做路线决策。

## 7. 三阶段路线图

### Phase A：二游切入与首个可展示产品

**目标**：用 Character Kit 验证“角色一致性 + 成套产物 + 可分享导出”的需求与付费意愿。

**核心功能**：

- Pack 契约与项目结构（manifest、素材角色、许可证、AI 披露）；
- 离线打包/校验/导出（本阶段即可做，不依赖生成模型）；
- 素材生成适配器（图像模型）：壁纸、头像、贴纸、封面；
- 一致性控制：参考图/角色卡/固定描述 + 人工可调；
- 分享页/导出说明（先文件，后网页）。

**依赖**：图像生成 API（成本/质量/合规）、二游同人政策清单、5–10 位种子创作者。

**验收**：

- 10 位外部创作者在无一对一帮助下完成一个包；
- ≥60% 愿意公开发布；≥30% 愿意在假设价格下付费或付定金；
- 单包成本可核算，返工率可接受；
- 每个目标游戏都有书面政策结论（可做/不可做/待确认）。

**不做**：游戏内 Mod、账号系统、市场、复杂 UI、视频生成。

### Phase B：通用 Mod 创作核心

**目标**：把“自然语言 → 可构建、可测试的 Mod 项目”跑通一个游戏，形成可复制的 adapter 模式。

**核心功能**：

- Game Adapter 接口：事实抽取、能力声明、版本矩阵、构建/测试命令、授权状态；
- Project Manager：spec → 项目脚手架 → 依赖锁定 → 变更历史；
- 代码生成 + 编译校验 + 构建失败诊断；
- 沙箱 Build & Test：构建、启动、日志采集、超时/清理；
- Diagnostic & Repair：现有 triage 迁入；新增构建失败与运行失败诊断；补丁候选需人工确认；
- 契约：分析契约 1.x 保持；新增项目/构建结果契约。

**依赖**：首个真 Mod 游戏的授权与工具链；跨平台构建环境；沙箱方案。

**验收**：

- 从一段自然语言 spec 生成一个可构建的 NeoForge（或获授权等价）项目；
- 在干净环境构建成功，并通过一个最小运行/加载测试；
- 注入 3 类典型失败（依赖冲突、API 误用、资源缺失），系统能给出证据化诊断且不编造；
- 修复建议经人工确认后可应用，并重新构建通过；
- 全流程产物均通过契约校验，无“看起来完成”的虚假状态。

**不做**：多游戏同时支持、自动发布、付费、复杂可视化编辑器。

### Phase C：平台、生态与商业化

**目标**：多游戏 adapter、创作者生态、可持续收入。

**核心功能**：

- 第二个/第三个游戏的 adapter（按授权与可行性排序）；
- 模板/风格包市场、创作者分成、团队协作；
- 可视化项目浏览与预览、版本对比、回滚；
- 分发与许可证管理、CI for Mods；
- 订阅/按量计费、配额与成本控制、商用授权。

**依赖**：A/B 的真实留存与付费数据；法务与平台合作；稳定的构建基础设施。

**验收**：

- 至少 3 个游戏的 adapter 可用，且各自有授权结论；
- 有真实的付费转化与复购，而非一次性尝鲜；
- 创作者能在平台上完成“创作 → 测试 → 分享 → 获得反馈”的闭环；
- 单位经济模型为正或路径清晰。

**不做**：无授权游戏、破解/注入、通用大模型平台、无边界的功能堆叠。

### 阶段闸门

- A → B：只有“包完成率 + 付费意愿 + 政策结论”同时达标才进入 B；否则调整形态（例如转为纯模板工具或纯诊断工具）。
- B → C：只有“单游戏闭环稳定 + 构建成功率 + 诊断准确率”达标才扩游戏；否则继续打磨一个 adapter。
- 任一路径若被证伪，保留 Crash Triage 作为独立产品线，不强行平台化。

## 8. 关键风险与待验证假设

### 8.1 风险

| 风险 | 影响 | 早期信号 | 缓解 |
| --- | --- | --- | --- |
| 二游 IP/同人政策收紧 | 产品直接不可用 | 官方政策变更、投诉、下架 | 逐游戏政策清单；只做允许范围；可切换到原创角色/授权 IP |
| 游戏内 Mod 授权缺失 | 无法兑现“真 Mod”承诺 | 官方无接口/明确禁止 | 周边与游戏内能力严格分层；不夸大支持范围 |
| 角色一致性不达标 | 产物不可分享，付费失败 | 盲评“不像同一角色” | 参考图锁定、角色卡、人工调参、种子管理 |
| 单包成本过高 | 毛利为负 | 每包调用次数/费用超预期 | 缓存、分级模型、批量、免费层限流 |
| 构建/运行沙箱逃逸或污染 | 安全与信任事故 | 子进程越权、残留进程 | 容器/受限用户、超时、白名单命令、清理 |

| 日志/素材隐私 | 合规风险 | 真实日志含个人信息 | 本地优先、脱敏、最小上传、明确保留策略 |
| 范围膨胀 | 资源分散 | 同时做多游戏/多形态 | 阶段闸门；每阶段明确“不做什么” |

## 9. 推荐下一项实际开发任务

### Phase 3.1：Pack 契约 + 离线打包最小纵向切片

**为什么是它**：

- 当前仓库在“写侧”完全空白：没有项目结构、没有素材清单、没有导出包、没有产物校验。这是创作平台的第一块地基。
- 它**不需要模型调用**，因此可以零 API 成本、可完全离线、可用 unittest 覆盖，符合“先确定性、后 AI”的原则。
- 它能立刻产出可给创作者看的东西（一个可解压、可分享的角色主题包），用于验证 A1/A2/A7，而不是继续在日志解析里自嗨。
- 它不触碰 `triage_agent.py`，不改变现有 107 个测试与 JSON 契约，风险可控。

**范围（只做这些）**：

1. 新增 `veyra_pack.py`（标准库），子命令：
   - `init <dir> --title ... --character ...`：创建项目骨架与 `pack.json`；
   - `validate <dir>`：确定性校验，退出码 0/2/1，输出可读问题列表；
   - `export <dir> -o <zip>`：原子生成 zip（含 manifest、素材、许可证、AI 披露），拒绝覆盖已有文件（除非 `--force`）。
2. 新增 `pack.schema.json` 与 `docs/pack-contract.md`（版本 `0.1.0`，与 CLI `schema_version` 独立）。
3. `pack.json` 最小字段：`pack_schema_version`、`pack_id`、`title`、`game_title`、`character`、`locale`、`license`、`ai_disclosure`、`assets[]`（`path`/`role`/`format`/`width`/`height`/`sha256`）、`outputs[]`。
4. 校验规则：
   - 必填字段与类型；`pack_schema_version` 主版本匹配；
   - 素材文件必须存在、位于项目目录内（拒绝 `..` 与绝对路径逃逸）；
   - 格式/尺寸与 `role` 匹配（如 `wallpaper` 需 16:9 且 ≥1920×1080；`avatar` 为正方形）；
   - 同一 `role` 不重复；`sha256` 与实际文件一致；
   - 缺许可证/署名/AI 披露时失败，不“自动补全”；
   - 导出时拒绝输出路径等于输入目录内文件、拒绝覆盖已有包（除非显式 `--force`）。
5. 测试：新增 `tests/test_pack_*.py`，≥25 个用例，全部在临时目录；覆盖非法 manifest、路径逃逸、尺寸不符、哈希不符、原子导出失败保留旧包、`--force` 语义。
6. CI：新增 pack 测试与 `export` 冒烟；不调用网络。
7. 文档：README 增加“Pack（实验性）”一节，明确“无生成、无游戏内注入、仅离线打包”。

**验收**：

- 在干净克隆中：`init` → 放入占位素材 → `validate` 退出 0 → `export` 生成可解压 zip；
- 8 类非法输入均以退出码 2 拒绝，并给出具体原因；
- 导出失败（模拟磁盘错误/占用）不留下半个 zip，旧文件保留；
- `python -m unittest discover -s tests` 全绿（107 + 新增）；
- 不修改 `triage_agent.py`、`report.md`、现有契约与 Skill；
- 用 3 个真实/人工角色各做 1 个包，交给目标用户试用并记录反馈。

**明确不做**：

- 不接图像/代码生成模型；
- 不做游戏内 Mod、不做注入；
- 不做 UI/账号/市场；
- 不重写现有 triage 或抽取 Core；
- 不承诺“一键生成整套图”。

**后续（Phase 3.2）**：在 pack 契约稳定后，接入一个图像生成适配器（先生成单角色 3 类产物），复用 `validate` 与 `export`，再评估一致性与成本。只有 A1/A2 得到正信号，才进入 Phase B。
