# Mod Issue Triage

把玩家或 Mod 作者描述不清的 Mod 问题反馈，整理成结构化、信息完整、方便后续处理的问题报告。本 Skill 只负责"信息整理"，不负责修复。

完整报告模板与示例见 [`references/report-template.md`](references/report-template.md)。

## 何时使用 / 何时不使用

**使用：**
- 用户带着模糊描述、聊天记录、日志或崩溃报告，希望先弄清楚"到底发生了什么"。
- 需要把零散信息整理成可交给 Mod 作者或测试人员跟进的标准问题报告。
- 需要识别还缺哪些关键信息，以便一次性向用户追问。

**不使用：**
- 直接修复 Bug、编写补丁或修改 Mod 代码。
- 启动游戏、运行测试或实际复现问题。
- 分析崩溃根因、判定责任或给出确定性结论。
- 自动提交 GitHub Issue 或调用任何外部服务。

遇到上述请求时，明确说明职责边界，并只交付本 Skill 能产出的问题报告。

## 输入要求

- **必需**：用户原始描述。可以很模糊，原样保留，不要改写事实。
- **可选**：环境信息，如游戏版本、Mod 版本、加载器、操作系统、其他 Mod 列表。
- **可选**：日志或崩溃报告文本。原样引用，不要补全。

信息缺失是常态。不要为了"报告完整"而编造；缺失项标注"未提供"或"不确定"。

## 执行步骤

1. **理解问题类型**：判断是报错/崩溃、功能异常、表现不符预期，还是普通提问；无法判断时按"未分类"处理。
2. **提取已有信息**：从描述、环境和日志中逐条抽取事实，并区分"用户确认的事实"与"用户的猜测"。
3. **识别信息缺口**：对照报告字段列出缺失项，并说明每项缺失会影响哪一步处理。
4. **整理复现步骤**：只用用户提供的信息排序；缺失的操作标注"未提供"，不要脑补。
5. **生成报告**：按模板输出；矛盾点单独标出，推断内容明确标注"推测"。

## 输出格式

默认用中文，按以下 Markdown 模板输出（完整版见 references/report-template.md）：

```markdown
# {问题标题}

## 问题现象
## 运行环境
## 复现步骤
## 还需要的信息
## 当前判断
## 免责声明
```

每个字段至少包含一句实质内容；没有内容时写"未提供"。

## 处理规则

- **区分事实与推测**：用户明确说过的写"用户确认"；由你推断的写"推测"，并说明依据。
- **信息不足不报根因**：信息不足时不得声称"已找到根因"，只能给出待验证的假设。
- **矛盾不自行选择**：前后信息冲突时标出"矛盾"，列出双方说法，让用户确认。
- **不编造版本号**：版本、加载器、Mod 列表都必须来自用户输入；未提供就写"未提供"。
- **不越界**：用户要求修 Bug、写代码、跑游戏、分析根因或提交 Issue 时，说明超出职责范围，并交付本报告。
- **保留原话**：关键报错信息和用户原话尽量原文引用，避免二次转述失真。

## 第一版边界

明确不做：

- 不修复 Bug，不编写或修改 Mod 代码。
- 不启动游戏，不运行测试，不实际复现。
- 不分析崩溃根因，不给出确定性修复方案。
- 不搜索互联网，不调用外部 API，不自动提交 GitHub Issue。
- 不做自动评估，不开发第二个 Skill，不设计大架构。

## 验收标准

1. 10 个测试案例中至少 9 个没有编造事实：版本号、复现步骤、根因判断均可在用户输入中找到依据。
2. 报告包含全部 7 个字段；缺失信息标注为"未提供"或"不确定"。
3. 输入存在矛盾时，报告中有明确的"矛盾"标记，且未自行取舍。
4. 用户要求直接修 Bug 或分析根因时，输出明确说明职责边界，且不包含修复代码或确定性根因结论。
5. "当前判断"中的推测均带"推测"标注，且能追溯到用户提供的信息。
